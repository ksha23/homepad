# Marking iMessages read from the hub: research

Date: 2026-11-05. Research only. Nothing was run against Messages, no settings changed, no other machine touched. The local checks in this report are static reads of signatures and bundle metadata on this Mac (macOS 27.0.1, build 26A434).

## Recommendation

Only one route has published, working code that marks a chat read with no window on screen: code injected into Messages that calls `[IMChat markAllMessagesAsRead]`. It needs SIP off. Everything that keeps SIP on drives the Messages UI, and the UI is what fails for background users and on a locked screen.

Ranked by how much of the five-person household each option can cover:

1. **Injected helper, SIP off (covers all five, expected but not proven for background users).**
   - What: launch each user's Messages with a helper dylib (`DYLD_INSERT_LIBRARIES`) that calls `markAllMessagesAsRead` on the chat. BlueBubbles Private API, imsg's bridge (MIT) and BBC (MIT) all do this. A HomePad-owned dylib with one command would be the smallest version.
   - Why it should reach background users: the call goes from Messages to that user's `imagent` with no window involved. BBC says its "Read and typing operations call native methods without opening a conversation". Nobody I found documents a test from a background Fast User Switching session or with the screen locked, so this is unverified.
   - Cost: SIP fully off (`csrutil disable` in Recovery, at the machine) and library validation off (`DisableLibraryValidation`), for the whole Mac. Kyle has to do both in person with an admin password. All five people's messages then sit on a host with weaker protections. Apple silicon Macs with SIP off cannot run iOS apps. Each macOS update can break injection.
   - Status: OpenClaw reports injection works on macOS 26.0 through 26.5.x with no boot-args. imsg issue 350 shows its injected bridge editing and unsending end to end on macOS 27.0.1. The BlueBubbles helper on master crashes Messages right after a mark-read request (issue 72, macOS 26.5.1), so do not take it unpatched.
2. **macOS virtual machines (covers at most three of five).**
   - What: each VM is its own console session that stays active and unlocked, so the hub's current "open the chat" method should work there. Apple lists Messages as working in a VM when host and guest run macOS 15 or later.
   - Limit: Apple silicon runs at most two macOS VMs at once (licence clause plus a kernel quota). Host console user plus two VMs is three people. The other two stay in background sessions.
   - Cost: RAM and disk for two more macOS installs, fresh installs from an IPSW, re-authentication if a VM moves. SIP could be turned off inside a VM only, leaving the host intact, but whether Apple Account sign-in still works in a VM with SIP off is unverified.
3. **Accessibility press of Conversation > Mark as Read, SIP on (likely covers only the user on screen).**
   - What: select the chat with the URL the hub already uses, then press the documented menu item through `AXUIElementPerformAction`. No keystrokes. Beeper's platform-imessage proves the explicit Mark as Read command marks read with SIP on, but it drives Messages in the session on screen.
   - Why it probably fails for the others: Apple says a switched-out session gets no keyboard or mouse input and sees the monitor as asleep. Keyboard Maestro's author says "you pretty much cannot do any UI when the Mac is screen sleeping, screen saving or screen locked." Neither tested an Accessibility menu press specifically, so this is unverified.
   - Cost: Accessibility permission per user, fragile to menu name and layout changes. Nothing system-wide changes, so it is the cheapest thing to try first.
4. **Screen Sharing "Log In" sessions held open per user (unknown coverage, speculative).** macOS lets a remote viewer log in as another user in a separate session. If each person's session stayed connected to a viewer, Messages might treat it as on screen. No source confirms that, and it needs an always-connected viewer per person.
5. **Protocol-level client per person (not recommended).** rustpush (OpenBubbles) implements `Read` (102) and `MessageReadOnDevice`, the signal that tells a person's own devices a message was read. It registers a new iMessage device with Mac hardware codes. Apple flagged Macs used this way in January 2024, and it puts a second, unofficial endpoint on each person's Apple ID.

**Fallback, already built:** HomePad's own read markers. Background users' iPhones stay unread.

**Suggested order if Kyle wants to test (one variable per test):** first option 3 from one background user, because it changes nothing system-wide. If Messages ignores the press, the choice is between option 1 (SIP off, all five) and option 2 (SIP on, three of five).

## 2. Can an unentitled, Developer ID signed process call IMCore?

No. `imagent` drops the connection.

- On macOS 26.3 the `imagent` log reads: "Client <pid> does not have any of allowed entitlements <private>, invalidating connection". `IMDaemonController.isConnected` stays false, so `IMChatRegistry` returns no chats. Ad-hoc signing with Apple's entitlements gets the process SIGKILLed. Using the listener ID `com.apple.MobileSMS` does not help. ([imsg issue 60](https://github.com/steipete/imsg/issues/60))
- BBC repeated this on macOS 27 with an ad-hoc probe and an Apple Development signed probe. Both were rejected with the same log line, even with SIP off and library validation off. "The connection call returned true while `isConnected` stayed false." ([BBC PR 18](https://github.com/lucasilverentand/BBC/pull/18), [sip-enabled-tapbacks.md](https://github.com/lucasilverentand/BBC/blob/main/docs/development/sip-enabled-tapbacks.md))
- The block is older than macOS 26. Barcelona already needed AMFI off on Big Sur to reach `imagent`. ([RUNNING.md](https://github.com/beeper/barcelona/blob/main/RUNNING.md))
- Local static check on macOS 27.0.1: the `imagent` binary contains the entitlement names `com.apple.imagent`, `com.apple.imagent.av`, `com.apple.imagent.chat` and `com.apple.private.imcore.imagent`. Messages.app is signed with `com.apple.imagent.chat`. Messages' Siri extension is signed with `com.apple.imagent`. The log redacts the allowed list, so which entitlement `imagent` actually requires is unverified.

What blocks each route, layer by layer:

1. `imagent` checks the XPC client's entitlements and invalidates clients without one of its allowed entitlements.
2. AMFI refuses to run a non-Apple binary that claims those restricted entitlements, unless AMFI is off (`amfi_get_out_of_my_way=1`, which needs SIP off).
3. Running inside Messages sidesteps both, because Messages already holds `com.apple.imagent.chat`. But SIP makes dyld ignore `DYLD_INSERT_LIBRARIES` for protected system apps, and library validation rejects a dylib not signed by Apple. That is why every injecting bridge needs SIP off and library validation off.

## 3. Does anything mark read from a background session or a locked screen?

Nothing documented does it with SIP on. Evidence by mechanism:

- **Messages' own read-on-view rule.** Apple says processes in a switched-out session "do not receive input from the keyboard and mouse. Similarly, if they were to check, the monitor would appear to be in sleep mode." ([Apple, Fast User Switching](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPMultipleUsers/Concepts/FastUserSwitching.html)) This matches what the hub sees: a chat only counts as read while it is on screen in an unlocked, active session.
- **Keystrokes posted to Messages (`CGEventPostToPid`).** Two developer forum reports say keyboard events posted by process ID only reach the app that owns the menu bar, or need the app brought to the front. No Apple reply. ([thread 695941](https://developer.apple.com/forums/thread/695941), [thread 724835](https://developer.apple.com/forums/thread/724835)) platform-imessage uses this, but with Messages activated in the session on screen.
- **UI scripting and Accessibility with the screen locked.** Keyboard Maestro's author: "you pretty much cannot do any UI when the Mac is screen sleeping, screen saving or screen locked." ([KM forum, 2019](https://forum.keyboardmaestro.com/t/macro-doesnt-work-when-mac-is-locked/15074)) A MacScripter thread reports the same for System Events GUI scripting. ([MacScripter, 2021](https://www.macscripter.net/t/gui-script-safari-when-screen-is-locked/73135)) Neither isolates an Accessibility press on a menu item, which is IPC to the app rather than an input event. So an `AXPress` of Conversation > Mark as Read in a background session is unverified, and the evidence leans against it.
- **The explicit menu command exists.** Apple documents Conversation > Mark as Read and Conversation > Mark as Unread in Messages for Mac. ([Apple, Keep track of messages](https://support.apple.com/guide/messages/keep-track-of-messages-ichtd3bb127f/mac)) platform-imessage shows the explicit command marks read with SIP on in the session on screen.
- **`open -g` or keeping the chat window open.** Neither changes whether Messages thinks the window is visible. In a background session the display appears asleep, so I expect no change. This is inference, not tested.
- **Shortcuts and App Intents.** On macOS 27.0.1, Messages' only App Intent is `ConversationListFocusFilterAction` (local check of `MessagesActionExtension.appex`, `Metadata.appintents`). BBC found the same on its 27 build. No mark-read action found in Shortcuts.
- **Siri extension.** Messages' Siri extension declares `INSetMessageAttributeIntent`, the SiriKit intent whose attributes include read and unread. It is signed with `com.apple.imagent`, so it could mark read with no UI. But only Apple processes can call an intents extension: Shortcuts and `siriactionsd` carry `com.apple.intents.extension.discovery` (local check). I found no third-party way to invoke it. Whether Mac Siri offers "mark as read" at all is unverified.
- **Injected IMCore call.** `markAllMessagesAsRead` needs no window. BBC states read "call[s] native methods without opening a conversation". I expect it to work in a background session and with the screen locked, because `imagent` runs per user regardless of the console. No source documents that test.

## 4. Mark-read with several macOS users on one Mac

No project documents it.

- BlueBubbles has a "Multiple Users on the Same Mac" guide in two versions. It covers a separate Firebase project, ngrok token and port per user, and says only one user can auto-login. It says nothing about the Private API, read state, background sessions or a locked screen. ([basic guide](https://docs.bluebubbles.app/server/basic-guides/multiple-users-on-the-same-mac), [advanced guide](https://docs.bluebubbles.app/server/advanced/multiple-users-on-the-same-mac)) A search of BlueBubbles issues for "locked screen", "lock screen" and "screen is locked" found nothing.
- BBC documents two macOS users under Fast User Switching on separate ports, and notes "SIP and library validation are settings for the whole Mac". Nothing on read from the background user. ([operating-modes.md](https://github.com/lucasilverentand/BBC/blob/main/docs/operating-modes.md))
- OpenClaw documents a "dedicated bot macOS user" for a separate iMessage identity, but not background behaviour. ([deployment](https://docs.openclaw.ai/channels/imessage/deployment))
- platform-imessage rules out multiple accounts. ([README](https://github.com/beeper/platform-imessage))

## 5. Other routes

- **macOS VMs.** Apple: in a VM "you can use services such as Messages, FaceTime and most iCloud features". The host and guest both need macOS 15 or later. iCloud Backup, Find My, media services and Wallet are unavailable. ([Apple 120468](https://support.apple.com/en-in/120468)) Apple silicon runs at most two macOS guests at once. A third fails with VZErrorDomain code 6, and the limit comes from licence clause 2B(iii), "up to two (2) additional copies or instances". ([Eclectic Light](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/)) Raising the kernel quota needs a development kernel with SIP off and is outside the licence. ([Koller, 2026-07-12](https://juergenkoller.software/en/blog/more-than-two-macos-vms-on-apple-silicon.html)) Reports conflict on whether upgraded VMs get iCloud, so build fresh from an IPSW. ([MacRumors](https://forums.macrumors.com/threads/macos-sequoia-adds-icloud-support-for-macos-15-virtual-machines.2429664/))
- **Screen Sharing sessions.** Screen Sharing can "log in as another user, and a session starts in the background that doesn't appear on the remote display screen" ([Six Colors, 2026-06-08](https://sixcolors.com/post/2026/06/high-performance-mode-allows-sharing-another-macs-display-as-if-your-own/)). A user report says a remote user beside a console user gets "a generic virtual screen created for the remote user" ([BetterDisplay discussion 2173](https://github.com/waydabber/BetterDisplay/discussions/2173)). Whether Messages treats a chat in such a session as on screen is unverified, and each person would need a viewer connected at all times.
- **Protocol client.** rustpush has `MessageReadOnDevice` ([messages.rs](https://github.com/OpenBubbles/rustpush/blob/master/src/imessage/messages.rs)). OpenBubbles needs "Apple hardware info" from a Mac ([FAQ](https://openbubbles.github.io/docs/faq)). In January 2024 Apple flagged Macs that supplied Beeper's registrations, then unbanned them after press coverage. Apple IDs were unaffected. ([9to5Google](https://9to5google.com/2024/01/26/beeper-imessage-disabled-apple-ban/))

## Ruled out, and why

| Route | Why ruled out |
|---|---|
| Writing chat.db | Given: no iCloud sync, Messages overwrites it |
| AppleScript | Given: no mark-read command. BBC's check of the installed `Messages.sdef` found only send, login and logout |
| Anything on the iPhone | Given: iOS gives apps no Messages access |
| Unentitled IMCore client, any signature | `imagent` invalidates it (section 2), on 26.3 and 27 |
| Re-signed copy of Messages.app | Re-signing drops Apple's restricted entitlements, and AMFI blocks claiming them without AMFI off (inference from imsg issue 60's SIGKILL result) |
| Injection with SIP on | dyld ignores `DYLD_INSERT_LIBRARIES` for protected system apps with SIP on. Every bridge refuses to try |
| Keystrokes to a background or locked session | Events posted by process ID reach only the menu-bar app (forum reports), and switched-out sessions get no input (Apple) |
| Messages App Intents or Shortcuts | Only a Focus filter intent on 27.0.1, no mark-read action |
| Invoking Messages' Siri extension | Needs `com.apple.intents.extension.discovery`, which only Apple processes carry (local check). No third-party path found |
| Apple command-line tools | Only `gamed` and `appleaccountd` in `/usr/bin`, `/usr/sbin`, `/usr/libexec` and CoreServices link IMCore (local check). Neither exposes Messages actions |
| Writing read state to CloudKit | Messages in iCloud uses Apple's private container and keys. Not reachable by a third-party process (inference, unverified) |
| Switching the console to each user to mark read | Each switch needs that user's password at the login window, shows on the Mac, and serves one person at a time |
| AirMessage, Jared, message-bridge | No mark-read at all |
| Barcelona, imessage-rest | Unmaintained, need AMFI off as well as SIP off |
| More than two macOS VMs | Licence and kernel quota |
